# 大榜单性能调查计划

日期：2026-10-20。范围：Vue renderer、demo2.json、RankLand 接入及 Chromium/Windows 机制。

## 授权与边界

- 先调研、测量、复现和提出优化方向；不修改产品实现，不 commit，不建分支或工作树。
- 保留现有 demo.json、demo2.json 和 CCPC26 文档工作。
- 独立测试脚本、构建和原始 trace 放临时目录；本目录记录可复核结论与测试方法。
- 低配实验使用隔离浏览器或已准备的 Windows VM；不对宿主机制造全局内存耗尽。

## 分阶段工作

1. **已完成：环境与基线**。固定数据、代码版本、构建方式和浏览器；已复现组件降速与 Windows 实页长任务。
2. **已完成：归因实验**。已完成响应式/行数/渲染阶段、曲线算法、真实页面 stable key 与空 Worker 对照；组件单变量三轮、生产构建和旧表强引用链均已验证。
3. **已完成：受限环境复现**。CPU slowdown 和真实 Windows VM 正常负载完成；已完成有退出阈值的VM压力实验；未复现自然导航崩溃，已明确边界。
4. **已完成：一手资料与接入审计**。Chromium/V8/Windows 官方资料及线上 sourcemap 核实完成，详见两个独立专题。
5. **已完成：综合报告**。区分实测、源码确定事实、机制支持推断与未证实项；给出基础/进阶优化、优先级和验收方法。

## 初始问题

- 首次打开是否出现秒级不可中断工作？消耗由数据还是组件/DOM 主导？
- 滚动、筛选、回放、改变显示选项是否重复全表工作？
- JS heap、Blink DOM/native 和 GPU 资源的体量及主因是什么？
- 低配 Windows 能否复现卡顿、页面无响应或 renderer crash？不能将人为 heap 限制等同真实 RAM。
- 保留全量 DOM 时有哪些有实测支持的低风险优化？虚拟化需要保留哪些功能契约？

## 环境问题

- 沙箱中 `prlctl list -a` 因 `/bin/ps: Operation not permitted` 无法初始化；将用授权的只读沙箱外检查确认 VM。
- 当前项目没有 Playwright 依赖，但机器有 Chromium 缓存；优先复用已安装测试运行时，不改依赖。
